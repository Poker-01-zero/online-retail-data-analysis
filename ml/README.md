# 复购预测

对截至观察点日末仍有有效购买记录的实名客户，用历史行为预测**之后 90 天内是否再次购买**，输出召回候选名单。观察点日末已全部取消购买的客户不进入样本，一次购买客户仍保留。

这是主项目（清洗 → 描述分析 → Tableau 看板）之上加的一层预测。数据和清洗口径与 MySQL 清洗层基本对齐，差异在下面「数据口径」一节说明，`data/online_retail_II.csv` 不被改动。

## 运行

```bash
python ml/run.py          # 全流程，约 2 分钟
python ml/test_features.py # 11 个特征回归测试
python ml/audit.py         # 全流程后重算对账与候选池统计
```

Windows 上 `python` 不在 PATH 时用完整路径：

```bash
C:\Users\lenovo\anaconda3\python.exe ml\run.py
```

依赖见 `requirements.txt`。

## 输出

| 文件 | 内容 |
|---|---|
| `outputs/metrics.csv` | 每个窗口、每个模型的 AUC、样本量、正例率 |
| `outputs/lift_table.csv` | 分档提升度：前 1%/5%/10%/20%/30%/50% |
| `outputs/lift_curve.png` | 提升度曲线 |
| `outputs/audit_summary.json` | 时间戳配对对账、未来取消影响、W3 候选池统计（由 audit.py 生成） |
| `outputs/churn_list.csv` | 召回优先级名单（客户 ID、复购概率、历史价值、优先级分） |

`docs/ab_test_design.md` 是配套的 A/B 实验设计稿：模型评估复购排序能力；候选池是否值得触达、发券是否有效，需实验验证。

## 结果

三窗口滚动验证，逻辑回归：

| 窗口 | 观察点 | 样本 | 正例率 | AUC | 前 10% 名单提升度 |
|---|---|---|---|---|---|
| W1 | 2011-02-28 | 4,502 | 35.1% | 0.784 | 2.49x |
| W2 | 2011-05-31 | 4,899 | 33.0% | 0.815 | 2.60x |
| W3 | 2011-08-31 | 5,216 | 42.8% | 0.789 | 2.10x |

- 三窗口平均 AUC 0.796
- 每个窗口都高于最好的单特征基线（W1 F=0.766、W2 R=0.775、W3 R=0.760）
- 窗口间波动 0.031
- 随机森林 AUC 与逻辑回归相差不到 0.007，因此选**逻辑回归**：系数可解释，能讲清每个特征的作用
- 这只说明三个窗口上的**整体排序指标**接近；不能推出每个客户的分数或每个名单的成员都没有变化

## 设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 标签窗口 | 90 天 | 约 1.7 个平均购买间隔（52.6 天）；365 天对应不同预测目标；不能仅凭正例率判断区分度 |
| 切分方式 | 按时间滚动 | 每个测试窗口只用它之前的数据训练；随机切分会让预测时点拿不到的信息进入训练 |
| 观察点 | T0 2010-11-30（热身）+ W1/W2/W3 | W1 没有更早的数据可训练，加 T0 后三个评估窗口都能用「只看过去」的模型 |
| 特征 | 11 个 | R、F、M、AOV、平均间隔、账龄、商品种数、取消次数、国家、近 90 天次数、上年同期 |
| 缺失值 | 训练集中位数填充 | 间隔对单次购买客户无定义（约 32%~35% 样本）；填充放在 Pipeline 里，只用训练集统计量 |
| 模型 | 逻辑回归 | 与随机森林效果几乎相同，可解释性更好 |
| 名单排序 | 历史消费金额 × 90 天未复购概率 | 生成候选实验池的启发式规则，触达收益尚未验证；不代表永久流失 |

## 时间一致性（这一层最容易出错）

**第 6 步清洗（剔除被取消的原始订单）必须按观察点重做。**

如果拿全期取消记录去删历史订单，就会出现：客户 2 月买的订单在 4 月取消，而站在 2 月底的预测代码已经把 2 月的购买删掉了。这属于用未来信息清洗历史。

实现方式：

- `load_data()` 只做到漏斗第 5 步，返回销售明细 + 取消明细
- `build_dataset(T)` 只用 `day <= T` 的取消记录重建快照，特征全部在这个快照上算
- 标签：先构建「标签结束日」的完整快照，再取 `(T, T+90]` 内的购买。只把窗口内的购买与取消放在一起配对会误删新购（见 `test_features.py` 的复现用例）
- 标签定义：窗口内产生、且截至标签结束日未被取消的购买

**未来取消影响量级**（固定当前时间戳匹配规则，仅比较全期取消与截至观察点取消；分母为该时点历史销售明细行数）：

| 观察点 | 被未来取消误删的行 | 受影响客户 | 占该时点历史行数 |
|---|---|---|---|
| T0 | 775 | 280 | 0.161% |
| W1 | 576 | 219 | 0.099% |
| W2 | 558 | 213 | 0.082% |
| W3 | 412 | 158 | 0.052% |

整体 AUC 从 0.796 前后基本未变，说明这类错误对**整体排序指标**影响很小；但受影响客户的 M、R、F 确实不同，名单顺序也会变。

## 数据口径

漏斗 1-5 步与 `mysql/05_build_clean_table.sql` 完全一致。第 6 步（取消配对）在 SQL 口径上**多了一条时间约束**：

| 口径 | 第 6 步规则 | 全期剔除 | 剩余行数 |
|---|---|---|---|
| SQL / 看板 | 每个 key 最多删 min(原始行数, 取消行数)，按日期截取最早几笔 | 6,665 | 996,548 |
| **ML 模块** | 同上，且要求**购买时间 <= 取消时间（保留时分秒）**，每笔销售/取消各用一次 | **6,067** | **997,146** |

差 598 行（占漏斗 1–5 步后记录的 0.060%）、营收差 £10,342.06。ML 全期营收 £19,092,681.79、实名客户 5,839 人。时间戳约束拒绝取消早于购买的匹配，包括同日内先取消、后购买的情况。

为什么只改 ML：预测的特征和标签都依赖时间先后，日期顺序错了会直接破坏时点逻辑；描述分析与看板保留已复核的 SQL 口径，两边数字的差异就是上面这 598 行，可对账。

**匹配本身的局限**：数据里没有「原始订单 ↔ 取消单」的外键，配对是按客户+商品+数量+价格四要素近似匹配。「数量约束 + 日期约束」能避免明显的误删，但无法证明每一笔都配对正确，所以影响数字应表述为**估算**。

有两处 MySQL 与 pandas 的细微差异，代码里已对齐并注释：

1. `CAST(Price AS DECIMAL(10,2))` 在过滤前先四舍五入，18 行标价 0.001 的记录（PADS/BANK CHARGES）按价格规则剔除
2. SQL 的 `REGEXP '^[0-9]{5}[A-Za-z]*$'` 匹配原始值，`'47503J '` 因尾随空格被拒绝；pandas 若先 strip 会多留这 1 行（£16.13）

## 局限

- 只在 W1~W3 三个时点上验证，W3 的标签窗口覆盖圣诞旺季，结论不代表全年
- 没有营销/触达字段，做不了 uplift 建模，也证明不了因果
- 排序效果由上述窗口的 AUC 验证；概率未做校准评估，不宜直接用于财务点估计
- 匿名订单（约 22.8%）没有客户 ID，不在建模范围内；实名子集本身有偏，结论只适用于实名客户
- 滚动验证中同一客户会同时出现在训练集和测试集（不同时点的快照），这是允许的；关键是测试时点的特征只用当时可得的信息
- 取消配对是四要素近似匹配，没有原始订单关联字段，无法逐笔确认；对匹配规则的敏感性分析尚未做
